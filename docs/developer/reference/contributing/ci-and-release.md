Semantic 由多个独立仓库组成。以下为跨仓协作与发布原则，具体自动化能力以各仓库实际配置为准，不代表所有仓库已有等价的公开 CI。

## 贡献流程

1. 从目标仓库指定的开发基线创建功能或修复分支。
2. 在 Issue 中说明现象、目标和验收方法。
3. 本地执行该仓库 README 中的测试与构建命令。
4. 提交 Pull Request，说明影响、兼容性和验证结果；通过审查后合入。
5. 跨仓变更在各仓分别关联 Issue / PR，更新 quick-start 的一致版本清单。

不要假定所有仓库默认分支名称一致，也不要在未验证的情况下合并不同发布基线。

## 测试层次

| 层次 | 目的 | 输入 |
|---|---|---|
| 单仓检查 | 格式、静态检查、单元测试、构建 | 当前仓库与锁定依赖 |
| 跨仓门禁 | 契约、Bundle 和前后端联调 | 匹配 revision 的组件工作区 |
| 仿真验证 | 原生依赖、场景加载与 Robot 执行 | 合法资产、Runtime 与完整 Bundle |
| 发布验收 | 安装、初始化、启动、停止和卸载 | 干净目标系统与候选制品 |

模型服务门禁可能调用外部付费接口，真机测试可能产生物理运动；必须显式配置并在受控环境执行。不能用跳过测试代替通过证明。

## 构建与版本

以 quick-start 的目录布局和清单为跨仓基准。构建依赖、Runtime Pack、Robot Bundle 与 Skill 包分别有版本，不应使用一个仓库的 Tag 推断所有产物版本。

公开 CI 需要可公开获取的工具链和依赖。镜像与代理是部署配置，不应依赖开发者个人环境或未公开的构建服务。

## 发布前检查

- 审查工作树及 Git 历史中的密钥、内部地址、个人路径与截图。
- 将克隆地址、依赖源及 CI 配置切换为公开可访问的来源。
- 保留第三方版权声明，逐项确认模型和二进制资产的分发许可。
- 记录 revision、制品哈希、兼容平台、迁移说明和实际验证结果。
- 发布后验证安装入口与版本清单，不覆盖不可变版本制品。

具体命令见 [构建、运行与测试](/developer/reference/build-run-and-test/)，贡献要求见 [贡献指南](/developer/reference/contributing/)。
